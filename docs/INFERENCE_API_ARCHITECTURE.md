# Inference API — Architecture

This document is the source of truth for the production inference API server.
Read it before touching anything under `src/serving/`, the gateway, worker
processes, or the HTTP contract.

## Context

The repo today is a CLI benchmark harness (`src/`, `bench/`) that drives a
single HuggingFace VLM via `src/engine.py::HFEngine` (transformers) and can
also call OpenRouter for comparison. There is **no HTTP API surface** yet —
FastAPI is in dependencies but no routes exist. The Streamlit frontend in
`bench/app.py` is a benchmark dashboard, not a chat UI.

We are evolving this into a **production-grade inference server** that exposes
local models (VLMs, LLMs, embeddings, and later OCR) on the LAN ("local
internet") so other services and humans can call them via plain HTTP — `curl`,
browser, or any OpenAI-compatible client. There will be no Verkos SDK; the
public contract is the HTTP API itself, so it has to be familiar and stable.

**Serving runtime: sglang.** Each model is hosted by an `sglang` server
process, which natively exposes OpenAI-compatible endpoints, continuous
batching, streaming, cancellation, and KV-cache management. We do **not**
write our own engine or adapter layer — sglang is the engine. The existing
`HFEngine` (transformers) stays in place for the bench harness only; it is
**not** part of the serving stack.

**Confirmed design choices:**
- API shape: **exact OpenAI / OpenRouter compatibility** — sglang gives us
  this for free at the worker layer; the gateway preserves it.
- v1 model types: **chat / VLM** + **embeddings**. OCR and legacy
  `/v1/completions` deferred — but the gateway must not block them.
- Topology: **one sglang process per model + thin gateway** in front.
- v1 reliability: **bearer API keys** (gateway-enforced, generated by a
  standalone Python script) + **health / readiness / metrics** endpoints.
  Rate limiting deferred to v2.

## High-Level Architecture

```
                            ┌────────────────────────────────────────────┐
   curl / OpenAI SDK ─────► │   Gateway (FastAPI, 0.0.0.0:8000)          │
   OpenWebUI / LangChain    │   - Bearer auth (keys.json)                │
                            │   - routes /v1/* by `model` field          │
                            │   - merges /v1/models from workers         │
                            │   - aggregates /metrics                    │
                            │   - SSE pass-through                       │
                            └─────────────┬─────────────┬────────────────┘
                                          │             │
                  ┌───────────────────────┘             └──────────────────────┐
                  ▼                                                            ▼
       ┌──────────────────────┐                                  ┌──────────────────────┐
       │ sglang server        │                                  │ sglang server        │
       │ 127.0.0.1:30001      │                                  │ 127.0.0.1:30002      │
       │ chat / VLM model     │                                  │ embedding model      │
       │ continuous batching  │                                  │ batched embed        │
       └──────────────────────┘                                  └──────────────────────┘
                  ▲                                                            ▲
                  └─────────────── shared GPU tower ───────────────────────────┘
```

**Why this topology:**
- Workers bind to `127.0.0.1` only and have no auth — they trust the gateway,
  which is the single ingress.
- Failure isolation: OOM in the VLM doesn't kill embeddings; restart one
  without touching the other.
- We write essentially **one** FastAPI app (the gateway). Workers are stock
  `sglang.launch_server` invocations — no Python code from us.
- Continuous batching and KV caching come from sglang; we don't reinvent
  them.

## Part A — HTTP API Contract (gateway-facing)

### A.1 Design Principles
- OpenAI / OpenRouter compatible: drop-in `base_url` swap should "just work".
- No SDK; the HTTP contract is the product. URLs, headers, JSON shapes are stable.
- Streaming via SSE (`text/event-stream`) — sglang produces standard OpenAI
  chunk format; the gateway streams it through unchanged.
- Predictable error envelope (`{"error": {"message", "type", "code"}}` like OpenAI).
- All clients identified by Bearer key; all responses log a `request_id`.

### A.2 Endpoints (v1)

| Method | Path | Purpose |
|---|---|---|
| GET  | `/v1/models` | Union of models advertised by healthy workers, with capability metadata |
| GET  | `/v1/models/{id}` | Detail for one model |
| POST | `/v1/chat/completions` | Chat — text and vision. Streams via SSE. |
| POST | `/v1/embeddings` | Text embeddings — batch input, returns dense vectors |
| GET  | `/healthz` | Liveness — gateway up |
| GET  | `/readyz` | Readiness — at least one worker healthy with a loaded model |
| GET  | `/metrics` | Prometheus exposition (aggregated across workers) |

Reserved for later (the gateway forwards to a worker if it advertises the
capability, returns 404 otherwise): `/v1/ocr`, `/v1/completions`, `/v1/rerank`.

### A.3 Request / Response Shapes

The gateway honors the **exact** OpenAI-compatible JSON schemas. Since sglang
already speaks this, the gateway's job for `/v1/chat/completions` and
`/v1/embeddings` is auth + routing + streaming pass-through; it does not
rewrite request or response bodies.

- **Chat completions** — `model`, `messages` (system/user/assistant with
  text-or-multimodal content parts including `image_url` with data URIs or
  http URLs), `temperature`, `top_p`, `max_tokens`/`max_completion_tokens`,
  `stop`, `seed`, `stream`, `stream_options.include_usage`, `n`,
  `response_format`, `user`. Response includes `id`, `object`, `created`,
  `model`, `choices[].message`/`delta`, `usage`. Anything sglang accepts, we
  pass through.
- **Embeddings** — `model`, `input` (string or array), `encoding_format`
  (`"float"` default, `"base64"` supported), `dimensions` (model-dependent),
  `user`. Response is standard `{data: [{embedding, index}], model, usage}`.
- **/v1/models** — sglang's `/v1/models` is augmented by the gateway with our
  `capabilities` block (`{chat, vision, embeddings, max_context_tokens,
  dtype}`) sourced from each worker's YAML, so clients can discover what each
  model supports without out-of-band knowledge.

### A.4 Streaming
- `text/event-stream` chunks (`data: {json}\n\n` ending in `data: [DONE]\n\n`).
- sglang generates the chunks; the gateway uses `httpx`'s streaming response
  to relay them byte-for-byte.
- Client disconnect → gateway aborts the upstream request → sglang cancels
  generation (sglang has native client-disconnect handling).

### A.5 Authentication
- `Authorization: Bearer <key>` on every `/v1/*` call. Enforced by the
  gateway; **workers do not check auth** — they're firewalled to localhost.
- Keys are stored in `keys.json` (gitignored), generated by
  `scripts/generate_api_key.py` (see §C). The gateway loads this file at
  startup and on SIGHUP.
- `/healthz`, `/readyz`, `/metrics` do not require auth (so probes work).
- 401 returns OpenAI-shaped error envelope.

### A.6 Errors
- Always JSON, always shape `{"error": {"message": str, "type": str, "code": str|null, "param": str|null}}`.
- HTTP status codes: 400 invalid_request_error, 401 authentication_error,
  404 model_not_found, 413 request_too_large, 422 unprocessable_entity,
  500 internal_error, 502 worker_error, 503 service_unavailable, 504 timeout.
- Every error response carries `x-request-id` header.
- Errors from sglang are wrapped to ensure the envelope matches our shape
  (sglang itself usually produces OpenAI-compatible errors, but we
  defensively normalize).

### A.7 Gateway Routing
- On startup: reads `gateway.yaml::workers` (list of `{name, url, capabilities}`),
  polls each worker's `GET /v1/models` and `/health` to confirm liveness,
  builds in-memory registry `{model_id → worker_url, capabilities}`.
- Per request: look up `model` field → forward to that worker via httpx with
  streaming pass-through. If model unknown → 404. If worker unreachable →
  marks it unhealthy, returns 503, retries health in background.
- Gateway adds `x-request-id`, propagates an auth-derived client identifier
  as an internal header (`x-verkos-client`) so per-key usage can be logged.
- `/v1/models` response is the union across healthy workers, enriched with
  per-model capability metadata.

### A.8 Observability
- Structured JSON logs via `python-json-logger` (already in deps): one log
  line per request with `request_id`, `model`, `route`, `status`,
  `latency_ms`, `prompt_tokens`, `completion_tokens`, `client_key_name`.
- `/metrics` (Prometheus) aggregates per-model counters: `requests_total`,
  `request_duration_seconds` (histogram), `tokens_total{kind=prompt|completion}`,
  `inflight_requests`, plus GPU gauges via `pynvml` (`gpu_memory_used_bytes`,
  `gpu_utilization_ratio` — reuse `src/gpu_poller.py`).
- `/healthz` always 200 if process is alive. `/readyz` 200 only when at least
  one worker reports a model is loaded.

### A.9 Deployment
- Each worker is an `sglang` process (see §B.2) bound to `127.0.0.1` on a
  fixed port.
- Gateway binds to `0.0.0.0:8000` for LAN access.
- `systemd` units (one per worker + one for gateway) for restart-on-crash.
  Workers must come up before the gateway is marked ready, but they can be
  launched in any order — the gateway polls and recovers.
- Single GPU box: workers share GPU 0; the operator sizes the fleet so total
  VRAM fits. Per-worker `CUDA_VISIBLE_DEVICES` is supported via env in the
  systemd unit when we get multi-GPU.

## Part B — Model Serving via sglang

### B.1 Why sglang (and what we no longer have to build)
- Native OpenAI-compatible endpoints (`/v1/chat/completions`, `/v1/embeddings`,
  `/v1/models`, `/health`).
- Continuous batching across in-flight requests — the previous transformers
  design serialized everything behind an `asyncio.Lock`; sglang fixes this at
  the engine level.
- RadixAttention KV-cache reuse (big win for repeated system prompts).
- Streaming + client-disconnect cancellation are native.
- Multi-modal (VLM) support for the major model families.
- Embedding mode (`--is-embedding`) for embedding models.

Because of this, we **delete the planned `src/serving/adapters/` layer
entirely**. The gateway is the only Python we write for the serving stack.

### B.2 Launching a Worker
A worker is just an sglang process. Model weights are placed on disk by the
operator (out of scope for this server); we only need a path. Example launch
command for a chat / VLM worker:

```bash
python -m sglang.launch_server \
  --model-path /models/<model-dir> \
  --host 127.0.0.1 \
  --port 30001 \
  --served-model-name <client-facing-id> \
  --mem-fraction-static 0.85 \
  --dtype bfloat16 \
  --chat-template <template-name>
```

For an embedding worker, add `--is-embedding` and drop the chat-template
flag. Any other `sglang.launch_server` flag is fair game — we pass them
through verbatim from the worker YAML.

We do **not** wrap these in custom Python. Launch via systemd unit or a tiny
helper script that converts `workers/<name>.yaml` → CLI flags.

### B.3 Per-Worker Config (`workers/<name>.yaml`)
A small YAML kept alongside the systemd unit. The launcher script translates
it to `sglang.launch_server` CLI args, and the gateway reads the
`capabilities` block to enrich `/v1/models`.

```yaml
worker:
  name: "chat-vlm"
  host: "127.0.0.1"
  port: 30001
sglang:
  model_path: "/models/<model-dir>"      # operator-provided
  served_model_name: "<client-facing-id>"
  dtype: "bfloat16"
  mem_fraction_static: 0.85
  chat_template: "<template-name>"
  is_embedding: false
  # Any other sglang.launch_server flag can be added here and is passed through.
capabilities:
  chat: true
  vision: true
  embeddings: false
  max_context_tokens: 32768
  max_image_pixels: 2_000_000
```

### B.4 Gateway Config (`gateway.yaml`)

```yaml
auth:
  keys_file: "/etc/verkos/keys.json"   # generated by scripts/generate_api_key.py
workers:
  - name: "chat-vlm"
    url: "http://127.0.0.1:30001"
    config_ref: "workers/chat-vlm.yaml"  # gateway reads capabilities from here
  - name: "embed-bge"
    url: "http://127.0.0.1:30002"
    config_ref: "workers/embed-bge.yaml"
server:
  host: "0.0.0.0"
  port: 8000
  log_level: "info"
gpu:
  poll_interval_s: 5.0
```

### B.5 Worker Lifecycle
- **Startup:** systemd starts sglang → sglang loads weights, warms up,
  exposes `/health`. Gateway polls each worker's `/health` and `/v1/models`
  on its own startup and on a 5 s background timer.
- **Readiness:** the gateway considers a worker ready when both `/health`
  returns 200 and `/v1/models` lists the expected `served_model_name`.
- **Shutdown:** systemd SIGTERM → sglang drains and exits. Gateway flips the
  worker to unhealthy on the next poll and starts returning 503 for that
  model.
- **Crash:** systemd restarts; gateway recovers automatically.

### B.6 GPU Memory
- `mem_fraction_static` in each worker's config caps how much VRAM sglang
  takes for its KV cache pool. Operator picks values so that sum across all
  workers + headroom ≤ total VRAM.
- `pynvml` reading (reuse `src/gpu_poller.py`) drives the `/metrics` GPU
  gauges. We do not try to reallocate memory at runtime.

## Part C — API Key Generation

Internal API → no DB, no admin UI. Keys are produced by a standalone Python
script and stored in a JSON file the gateway reads.

### C.1 Script: `scripts/generate_api_key.py`

Standalone CLI. Generates a cryptographically random key, writes a record to
`keys.json`, prints the key to stdout **exactly once** so the operator can
copy it to the client.

Usage:

```bash
# Generate a key for "data-team", append to default keys file (./keys.json)
python scripts/generate_api_key.py --name data-team

# Specify the keys file path
python scripts/generate_api_key.py --name alice --keys-file /etc/verkos/keys.json

# List existing keys (names + created_at + prefix only; full key never printed again)
python scripts/generate_api_key.py --list

# Revoke a key by name
python scripts/generate_api_key.py --revoke data-team
```

Behavior:
- Key format: `sk-flytbase-airr-<43 url-safe chars>` (i.e. `secrets.token_urlsafe(32)`).
- Refuses to overwrite an existing name; use `--revoke` first.
- `keys.json` is created with mode `0600` if it doesn't exist.
- Each record: `{"name": str, "key": str, "created_at": ISO8601,
  "revoked_at": ISO8601 | null}`.
- Listing prints `name | created_at | revoked_at | key_prefix (first 12 chars)` —
  never the full key.
- No external dependencies beyond Python stdlib.

### C.2 `keys.json` Shape

```json
[
  {
    "name": "data-team",
    "key": "sk-flytbase-airr-AbCdEfGh...",
    "created_at": "2026-05-22T10:15:00Z",
    "revoked_at": null
  }
]
```

### C.3 Gateway Behavior with `keys.json`
- Loaded at startup; each non-revoked key is added to an in-memory set, and
  a `key → name` map is kept for logging.
- SIGHUP reloads the file (so revoking a key takes effect without restart).
- Missing file → gateway refuses to start with a clear error.
- A request with `Authorization: Bearer <unknown-or-revoked>` → 401 with
  OpenAI-shaped error envelope.

### C.4 Operational Notes
- `keys.json` is gitignored. Document this in README and in the script's
  help output.
- Recommend keeping it in `/etc/verkos/` with the gateway process user as
  the only reader.
- Revoking does not delete; it sets `revoked_at` so audits remain intact.

## File Layout

```
docs/
  INFERENCE_API_ARCHITECTURE.md      # this file
src/serving/                          # gateway only — workers are stock sglang
  __init__.py
  app.py                              # FastAPI gateway
  config.py                           # Pydantic schemas for gateway.yaml + worker.yaml
  auth.py                             # Bearer key loader + checker (reads keys.json)
  registry.py                         # Worker discovery + health polling
  proxy.py                            # httpx streaming pass-through
  errors.py                           # OpenAI-shaped error envelope helpers
  metrics.py                          # Prometheus registry, GPU gauges (uses src/gpu_poller.py)
  __main__.py                         # python -m src.serving --config gateway.yaml
scripts/
  generate_api_key.py                 # API key generation CLI (stdlib only)
  launch_worker.py                    # tiny YAML → sglang.launch_server CLI translator
workers/
  chat-vlm.yaml                       # sglang launch args + capabilities
  embed-bge.yaml
gateway.yaml                          # gateway config
keys.json                             # gitignored; created by generate_api_key.py
deploy/
  systemd/
    verkos-worker@.service            # templated unit: instance arg = worker name
    verkos-gateway.service
```

The bench harness (`src/engine.py`, `src/feed_runner.py`, `bench/`,
`src/__main__.py`, `src/config.py`) is untouched and continues to use
transformers via `HFEngine` — it has nothing to do with the serving stack.

## Deferred to v2

- Rate limiting & per-key quotas (sglang gives us throughput; fairness is
  the open problem).
- OCR endpoint (`/v1/ocr`) + dedicated OCR worker.
- Legacy `/v1/completions`.
- Tool / function calling.
- JSON-mode / structured outputs.
- Reranking (`/v1/rerank`).
- Multi-GPU sharding via `CUDA_VISIBLE_DEVICES` per worker (config plumbing
  is ready; we just haven't exercised it).

## Verification

**Phase 2 (API key script):**
- `python scripts/generate_api_key.py --name test` prints a key starting with
  `sk-verkos-` and appends to `keys.json`.
- Running the same command twice refuses with a non-zero exit and clear error.
- `--list` shows the name and prefix but not the full key.
- `--revoke test` marks the record `revoked_at` non-null without deleting it.
- `keys.json` permissions are `0600`.

**Phase 3 (chat worker direct):**
- `curl http://127.0.0.1:30001/v1/models` returns the configured model.
- `curl -X POST http://127.0.0.1:30001/v1/chat/completions -d '{"model":"<served_model_name>","messages":[...]}'` returns an OpenAI-shaped response.
- For a VLM, image input via `image_url` data URI or http URL works.

**Phase 4 (gateway):**
- `curl http://localhost:8000/v1/models` lists model(s).
- Missing/invalid `Authorization` → 401 with OpenAI error envelope.
- Valid key → request proxied; response identical to hitting the worker
  directly.
- `stream: true` returns SSE chunks ending in `data: [DONE]`.
- Killing the client mid-stream stops generation upstream (verify GPU drop
  via `nvidia-smi`).
- OpenAI Python SDK pointed at `http://<host>:8000/v1` with any valid key
  works without modification.

**Phase 5 (multi-model):**
- `/v1/models` returns the union of chat and embedding models with
  `capabilities` populated.
- `/v1/embeddings` against the embed model returns vectors; against the chat
  model returns 404 model_not_found-style error (or routes correctly if both
  capabilities exist).
- Killing one worker flips its models out of `/v1/models` and `/readyz`
  stays 200 as long as any other worker is healthy.
